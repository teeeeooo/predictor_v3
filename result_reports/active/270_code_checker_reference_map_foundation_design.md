# 270 Code Checker Reference Map Foundation Design

## Goal

Design a lightweight `code_checker` for predictor_v3 that provides a
machine-readable + human-readable codebase map to reduce repeated audits and
rediscovery of existing helpers, adapters, and surfaces.

This is a design slice. No code, scripts, tests, or folders are created.

## Background

The predictor_v3 codebase has grown to ~260+ reports across active, summaries,
and archive. Recurring patterns observed:

- Re-auditing existing helpers/adapters because prior session state is lost
- Soft-limit files growing unnoticed (metric_input_table.py 445 LOC,
  excel_like_table_controller.py 401 LOC)
- Reference parity checks requiring manual cross-file search
- New surface creation without checking existing `TkTableSurface`
  implementations

Existing guard `tools/check_code_structure.py` covers layer imports, app
entrypoint thinness, LOC/class soft limits, and allowlist management. It is a
structural linter, not a semantic map generator.

The gap: a compact, updatable reference map that an agent can read in a new
session to answer "what helpers already exist for X?" and "which files are near
the soft limit?"

## Fit Assessment

**Verdict: Worth adopting, conditional on MVP scope.**

**Expected benefits:**
- Reduce repeated reference-parity audits before new helper creation
- Surface soft-limit hotspots before they become blockers
- Provide cross-session memory of symbol locations
- Complement (not replace) `check_code_structure.py`

**Expected limitations:**
- Map is evidence, not source of truth. AGENTS.md, architecture docs, and
  WORK_PLAN remain the canonical rules.
- Map can become stale if not updated. The design includes an update hook
  policy, not a promise of automatic freshness.
- Semantic accuracy is limited to static analysis (imports, symbols, LOC).
  Runtime behavior and design intent are not captured.

## Owner / Folder Boundary Decision

**Recommended: `tools/code_checker/`**

Rationale:
- `tools/` already contains `check_code_structure.py` and other dev aids.
- Keeping code checker alongside existing structural guard makes the tooling
  boundary obvious.
- Agent prompts can refer to `tools/code_checker/` without ambiguity.
- Future CI/guard integration can point to `tools/` without adding a new
  top-level folder.

**Rejected alternatives:**
- `dev_tools/`: Creates a new top-level folder that blurs the boundary between
  project product and developer tooling.
- Root-level script: Mixes with actual application entrypoints (`app_*.py`).
- `scripts/`: Already used for operational/packaging scripts; analysis tooling
  is a different responsibility.

**Relationship with `check_code_structure.py`:**
- `check_code_structure.py` is a pass/fail structural guard (layer imports,
  LOC limits, allowlists).
- `code_checker/` is a map generator + evidence renderer (symbol inventory,
  hotspots, duplicates, import graph).
- They can share a Python AST visitor helper in a future slice, but MVP keeps
  them independent.

## Tracked vs Ignored Output Decision

**Tracked compact map:**
- `docs/code_map/CODEBASE_REFERENCE_MAP.md`
- Rationale: human-readable, compact, useful across Codespaces/iMac/Windows.
- Updated manually or via script in implementation slices.
- Commit frequency: per significant architectural change, not per PR.

**Ignored detailed cache:**
- `.code_checker/` or `.local/code_checker/`
- Rationale: detailed JSON/symbol dumps change frequently and create noise.
- Generated by script on demand; not committed.
- `.gitignore` update deferred to the implementation slice that creates the
  script.

**Environment ping-pong mitigation:**
- The compact Markdown map is the shared reference.
- Detailed JSON is local-only and reproducible from source.
- No environment-specific paths or secrets in either output.

## MVP Scope

**Included:**

1. Python file inventory (excluding tests, reports, docs, cache)
2. Per-module LOC / class count / top-level function count
3. Top-level symbol map (classes, functions, constants) with line numbers
4. Import edge collection (which module imports which)
5. Duplicate symbol name candidates (same name in different files)
6. Known owner keyword groups (table, calculator, window, detail, export, etc.)
7. Soft-limit hotspot list:
   - Files > 250 LOC
   - Files with > 3 classes
   - Functions > 60 LOC
   - Files near the 400 LOC soft limit (with allowlist respect)
8. Compact Markdown rendering of the above

**Excluded (future phases):**

- Semantic clone detection
- Full call graph / callee-caller mapping
- Runtime dependency analysis
- CI / pre-commit hook integration
- Lumin Repo Lens plugin installation or direct integration
- HTML / interactive visualization
- Incremental diff-based updates (MVP is full rebuild)

## Map Document Shape

`docs/code_map/CODEBASE_REFERENCE_MAP.md` sections:

1. **Generated note** — last updated task number, generator version, caveat
   that this is evidence not source of truth.
2. **Layer overview** — core/, ui_tk/, tests/, docs/, tools/ file counts and
   total LOC.
3. **Owner groups** — table-shaped UI, window/dialog, calculator/core,
   result/detail/export, batch, ML/predictor, report/docs tooling.
   Each group lists key files and their primary symbols.
4. **Hotspot files** — files exceeding or near soft limits, with current metrics.
5. **Duplicate / adjacent helpers** — symbol names appearing in multiple files
   that may indicate reusable extraction candidates.
6. **Import edges** — key cross-layer imports (e.g. which ui_tk files touch
   core.calculator_dispatcher).
7. **How to use before implementation** — short checklist for agent sessions.

**Design constraints:**
- Total length target: under 300 lines.
- No full source code excerpts.
- Symbol names + file paths only.
- Update trigger: after significant architectural changes or before large
  migrations.

## Workflow Hook Policy

**Run code checker BEFORE:**
- New helper / adapter / table surface / controller creation
- ui_tk folder cleanup or controller switch preflight
- New profile UI surface addition
- Python calculator integration or core surface change
- Result / detail / export commonization

**Run code checker AFTER:**
- Implementation to verify no new hotspots introduced
- Refactoring to verify symbol moves are reflected

**Do NOT run for:**
- Report-only closeout or lifecycle maintenance
- Windows smoke result reflection
- Test expectation correction
- Wording / typo fixes
- Golden fixture updates
- Single-file hotfixes with no new symbols

**Pre-write usage:**
- Search the map for existing symbols matching your intent.
- Check hotspot list before adding responsibility to a soft-limit file.
- Verify import edge to ensure layer boundary compliance.

**Post-write usage:**
- Add a "Reference Evidence" section to the result report citing:
  - Existing symbols reused (or why not reused)
  - New hotspots created (or why not created)
  - Import edge changes

## Risks

- Map staleness: if not updated, the map becomes misleading evidence.
  Mitigation: workflow hook policy and explicit "last updated" header.
- Over-reliance: agents may treat the map as source of truth instead of
  AGENTS.md/architecture docs. Mitigation: document header explicitly states
  "evidence, not source of truth."
- Scope creep: adding semantic analysis, call graphs, or CI hooks before MVP
  stabilizes. Mitigation: strict MVP boundary and explicit future-phase list.
- `.gitignore` noise: if cache is accidentally committed. Mitigation:
  `.gitignore` update is part of the MVP implementation slice.

## Project Memory Delta

- predictor_v3 will adopt a lightweight `tools/code_checker/` for codebase
  reference mapping.
- Map output is split: compact Markdown (tracked, shared) and detailed JSON
  (ignored, local).
- Map is evidence, not rule. AGENTS.md, architecture docs, and WORK_PLAN remain
  canonical.
- Existing `tools/check_code_structure.py` is a structural guard;
  `code_checker/` is a semantic map generator. They are complementary.
