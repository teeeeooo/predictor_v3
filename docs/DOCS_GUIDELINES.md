# 문서 작성 지침

## 1. 문서 철학

이 프로젝트의 `docs`는 단순 설명서가 아니라 규격 구현 자산이다. 각 문서는 계산식을 옮겨 적는 메모가 아니라, 규격 해석과 구현 판단, 제품 설계 관점의 의미를 장기적으로 재사용할 수 있게 축적해야 한다.

문서는 다음 세 독자를 동시에 고려한다.

| 독자 | 필요한 정보 | 왜 중요한가 |
| --- | --- | --- |
| 미래의 나 | 당시의 해석 근거, 결정 이유, 검증 상태 | 시간이 지난 뒤에도 같은 판단을 반복하지 않기 위함 |
| AI Agent / 개발자 | 계산 순서, 입력/출력, 예외 조건, 흔한 실수 | 규격 구현 품질을 일관되게 유지하기 위함 |
| 냉동공조 제품 설계 엔지니어 | 성능 지표가 실제 제품 설계에 주는 압력 | 수치 개선이 실제 설계 방향으로 이어지게 하기 위함 |

## 2. 규격별 기본 문서 구조

각 규격은 원칙적으로 아래 3개 문서로 분리한다.

```text
docs/<standard>/
- <standard>_notes.md
- <standard>_dev_notes.md
- <standard>_design_notes.md
```

용어집은 규격별 상세 문서에 중복 작성하지 않고 `docs/glossary/` 하위에서 관리한다.

예:

```text
docs/en14825/en14825_notes.md
docs/en14825/en14825_dev_notes.md
docs/en14825/en14825_design_notes.md
```

| 파일 | 역할 | 포함해야 할 내용 |
| --- | --- | --- |
| `<standard>_notes.md` | 규격의 기준 문서 | 규격 개요, 계산 구조, 입력/출력 스키마, 수식과 코드 매핑, 검증 결과 |
| `<standard>_dev_notes.md` | 개발자와 Agent를 위한 구현 지침 | 코드 구현 노하우, 구현 실수 방지, 디버깅 방법, 테스트 전략, agent 재사용 프롬프트. glossary 본문은 포함하지 않고 필요 시 `docs/glossary/` 링크만 둔다. |
| `<standard>_design_notes.md` | 제품 설계 엔지니어를 위한 해석 문서 | 코드 언급 금지, 실제 제품 설계 관점, 효율 측정값을 높이는 설계 전략, 규격 구조에서 도출되는 정량적 인사이트. 5~10개 핵심 용어로 구성된 `Quick Glossary`를 포함하고, 상세 glossary는 `docs/glossary/` 문서를 참조한다. |

이 분리는 문서 품질의 핵심이다. 구현 판단과 제품 설계 판단은 서로 영향을 주지만, 같은 문단에 섞이면 독자가 근거와 응용을 구분하기 어려워진다.

`<standard>_design_notes.md`의 `Quick Glossary`는 상세 용어 사전이 아니라 설계자가 문서를 읽기 전에 알아야 할 핵심 용어 요약이다. 각 용어는 정의보다 물리적 의미와 제품 설계에 미치는 영향을 중심으로 적고, 공통 용어의 상세 설명은 `docs/glossary/` 하위 문서에 단일 출처로 유지한다.

## Future Refactor Notice

현재의 문서 구조는 임시적이다. 향후 `docs/REFACTOR_PLAN.md`에 명시된 트리거 조건이 충족되면, 문서는 역할별로 완전히 정규화될 예정이다. 그때까지는 현재의 규격별 폴더 구조를 엄격하게 유지한다.

## 3. 절대 금지 규칙

| 금지 항목 | 이유 |
| --- | --- |
| 코드 노하우와 설계 노하우 혼합 금지 | 구현 제약을 제품 설계 원리처럼 오해하지 않기 위함 |
| 근거 없는 추정 금지 | 규격 문서는 재사용 가능한 근거 자산이어야 하기 때문 |
| "추후 작성", "TODO만 남김", "대략" 같은 빈 문서 금지 | 빈 문서는 Agent와 개발자의 판단 품질을 떨어뜨림 |
| 규격 조항 번호 없이 핵심 주장 금지 | 주장과 원문 근거를 추적할 수 있어야 함 |
| 규격 수식과 코드 구현을 혼동 금지 | 규격의 원식, 프로젝트의 단순화, 예외 처리는 구분되어야 함 |
| `design_notes.md`에서 코드 파일명, 함수명, 변수명 언급 금지 | 제품 설계 관점 문서가 구현 세부사항에 종속되지 않게 하기 위함 |
| `dev_notes.md`에 glossary 본문 작성 금지 | 구현 지침과 용어 설명이 섞이지 않게 하며, 필요 시 `docs/glossary/` 링크만 사용하기 위함 |
| 공통 용어 중복 작성 금지 | glossary는 `docs/glossary/` 하위에서 단일 출처로 관리하기 위함 |

## 4. 근거 표기 규칙

핵심 설명에는 아래 형식 중 하나를 반드시 붙인다.

| 근거 유형 | 표기 형식 |
| --- | --- |
| 조항 | `Clause X.X.X` |
| 표 | `Table X` |
| 부속서 | `Annex X` |
| 수식 | `Equation X` |
| 부록 | `Appendix X` |

예:

- `EN14825:2012 Clause 6.4.2.2`
- `EN14825:2012 Table 36`
- `AHRI 210/240-2026 Section 11.2.2`
- `AHRI 210/240-2026 Table 16`

규격 원문 근거와 프로젝트 해석은 같은 문장에 섞어 쓰지 않는다. 먼저 규격 근거를 제시하고, 다음 문장에서 "프로젝트 해석:" 또는 "엔지니어링 해석:"으로 구분한다.

## 5. 문서 품질 기준

문서는 최소한 아래 질문에 답할 수 있어야 한다.

| 질문 | 합격 기준 |
| --- | --- |
| 이 문서만 보고 계산 구조를 복원할 수 있는가? | 입력, 중간 계산, 출력, 계절 합산 흐름이 순서대로 설명되어 있음 |
| 이 문서만 보고 구현자가 흔한 실수를 피할 수 있는가? | 단위, 보간, 보정계수, 경계 조건, 누락 데이터 처리 규칙이 명시되어 있음 |
| 이 문서만 보고 설계자가 성능 향상 방향을 잡을 수 있는가? | 어떤 운전점과 부하 구간이 등급에 큰 영향을 주는지 설명되어 있음 |
| 규격 근거와 엔지니어링 해석이 구분되어 있는가? | Clause/Table/Equation 근거와 해석 문장이 분리되어 있음 |

## 6. 문체 규칙

| 규칙 | 설명 |
| --- | --- |
| 한국어로 작성 | 프로젝트 내 지식 축적의 기본 언어를 통일한다. |
| 기술 용어는 최초 등장 시 영어 병기 | 예: 성능계수(Coefficient of Performance, COP) |
| 수식/변수명은 규격 표기 우선 | 프로젝트 내부 이름보다 규격 원문 표기를 먼저 쓴다. |
| 짧은 메모체 금지 | 문서만 읽어도 판단 배경을 이해할 수 있게 완결된 문장으로 쓴다. |
| 표를 적극 사용 | 조건, 입력, 출력, 예외, 검증 결과는 표가 가장 재사용성이 높다. |
| "왜 중요한지"를 반드시 설명 | 계산 규칙이 성능 평가와 제품 설계에 주는 영향을 함께 적는다. |
