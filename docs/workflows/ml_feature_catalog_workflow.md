# ML Feature Catalog Workflow

> **Current owner boundary:** Data Definition owns user-facing schema and
> feature-definition changes. The former Train/Admin Feature Catalog UI has
> been retired. `core/ml/feature_catalog*` and `config/ml/features.csv` remain
> an internal ML compatibility contract for training headers, projections, and
> model fingerprints.

## Purpose

`config/ml/features.csv` remains the compatibility contract for ML feature,
target, and one-hot feature names. Normal schema changes are made through the
`Data Definition` tab in `app_train.py`; there is no separate Feature Catalog
manager or canonical-save UI. Direct catalog editing is an exceptional,
explicitly reviewed developer maintenance action.

The central rule is:

```text
ml_name = raw training data header = internal ML feature or target name
```

There is no separate training header alias or header mapping layer. Training
data must use the catalog `ml_name` values directly.

## Edit Flow

For normal schema/feature-definition changes:

1. Open `app_train.py` and select the `Data Definition` tab.
2. Review schema, projection parity, mapping requirements, and model-readiness
   validation before editing.
3. Use only the guarded Data Definition draft/save flow. Respect any blocked
   field, restart-required, or retrain-required result.
4. Stop if the change requires a `features.csv` compatibility projection write;
   the current Data Definition writer does not own that write target.
5. Align raw training headers to the active catalog `ml_name` contract.
6. Run the focused catalog, Data Definition, and ML guard tests.
7. Restart or retrain when the validated change reports that impact.

If explicit maintenance of the internal compatibility catalog is approved, use
this bounded developer workflow:

1. Edit `config/ml/features.csv` directly.
2. Add or update one row with a non-empty `ml_name`; this is the catalog row
   primary identity, raw training data header, and internal ML feature or target
   name.
3. Set `role` to one of `input`, `auto`, `result`, `derived`, `one_hot`, or
   `hidden`.
4. Fill role-specific fields:
   - `input`: `ui_key`, `label`.
   - `auto`: `ui_key`, `label`, `source`, `mapping_key`.
   - `result`: `ui_key`, `label`.
   - `one_hot`: `one_hot_group`.
   - `derived`: no formula in CSV; formulas stay in code.
   - `hidden`: no direct UI column.
5. Set `zero_fill_policy`.
6. Save the file as UTF-8 comma-delimited CSV without BOM.
7. Align the training CSV or Excel export header to the catalog `ml_name`.
8. Confirm Data Definition projection parity and run the focused catalog and ML
   guard tests before training.
9. Train only after the guard tests pass.

## Compatibility Catalog Fields

The internal compatibility CSV contains:

- `order`
- `ml_name`
- `role`
- `ui_key`
- `label`
- `source`
- `mapping_key`
- `one_hot_group`
- `zero_fill_policy`
- `active`
- `notes`

## Code-owned Fields

Do not add these to `features.csv`:

- width or color;
- UI delegate/editor behavior;
- table widget settings;
- RFE settings;
- `model_key`;
- target-specific exclude or allowed rules;
- derived formulas;
- model artifact schema.

Width and color are derived in code from role defaults. Dropdown-only predictor
input columns and rule-only result columns are owned by
`core/predictor_schema/ui_columns.py`, not by the ML feature catalog.

## Role Notes

- `input`: user-entered ML feature exposed through predictor schema.
- `auto`: mapping-backed ML feature exposed through predictor schema.
- `result`: model target and result UI projection.
- `one_hot`: encoded ML feature generated from a grouped categorical input.
- `derived`: code-calculated feature generated by preprocessing.
- `hidden`: active internal feature that has no direct UI column.

Predictor UI-visible ML columns are ordered by role group and catalog order:

```text
input -> auto -> result
```

Rows inside each group follow the catalog `order`.

## One-hot Features

One-hot feature lists come from catalog rows with `role=one_hot`.

Current groups:

- `refrigerant`: `R410A`, `R32`, `R290`
- `expansion_device`: `EEV`, `Capi`

The Predict adapter still maps UI input keys to those groups:

- `ref_type` -> `refrigerant`
- `exp_type` -> `expansion_device`

## Zero-fill Policy

`zero_fill_policy` allowed values:

- `disallow`
- `mode_missing_allowed`

Only these four `ml_name` values may use `mode_missing_allowed`:

- `Cooling Capa`
- `Cooling Power`
- `Heating Capa`
- `Heating Power`

All other missing ML features fail fast during inference. This prevents
mapping, autofill, schema, or data-quality problems from being hidden as `0.0`.

## Training Data Contract

Training data headers must match active catalog `ml_name` values for raw
training roles:

- `input`
- `auto`
- `one_hot`
- `result`

Derived feature headers are not required in raw training data because derived
features are calculated by preprocessing code.

If a training CSV or Excel export has headers that are not catalog `ml_name`
values, training fails before fitting. If required catalog headers are missing,
training also fails before fitting.

## Model Compatibility

Training artifacts store a Feature Catalog fingerprint. Prediction model load
compares that fingerprint with the current catalog.

- If the artifact fingerprint is missing, retrain the model.
- If the artifact fingerprint differs from the current catalog, retrain the model.
- The model compatibility fingerprint includes active rows only, using these ML
  contract fields: `ml_name`, `role`, `one_hot_group`, and `zero_fill_policy`.
- Toggling `active` changes the fingerprint by including or excluding that row,
  not by storing `active` inside each payload row.
- Changing `label`, `notes`, `order`, or `ui_key` does not change the model
  compatibility fingerprint.
- `source` and `mapping_key` affect UI/input mapping and schema apply concerns,
  but are not part of the model artifact compatibility fingerprint.
- A separate UI schema fingerprint remains a future option; it is not wired at
  runtime by this workflow.

## CSV Editing Notes

When reviewing with Numbers or Excel:

- keep the comma delimiter;
- use a disposable review copy if UTF-8-SIG is needed for spreadsheet
  auto-detection; keep the canonical file UTF-8 without BOM;
- do not expect a Train/Admin catalog import or export surface;
- do not rename headers in the training export unless the same `ml_name` change
  is made in `features.csv`;
- do not add visual presentation fields such as width or color.

## Quick Checks

Run these focused checks after catalog edits:

```bash
python3 -B -m pytest tests -k "feature_catalog"
python3 -B -m pytest tests -k "training or train or inference or ml"
python3 -B -m pytest tests -k "predict_schema or prediction_adapter or prediction_usecase or apps_predict"
```

Do not start model training until these checks pass.
